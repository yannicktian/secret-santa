Comment le site est construit

Le site tel que l'epic #1 le construit. La spec du tirage fait foi pour le comportement et les mots ; le découpage donne les tâches ; l'avancement vit dans l'issue de l'epic.

Le Markdown fait foi : docs/architecture.md.

Vue d'ensemble

  • Pages statiques dans public/, servies telles quelles : pas de framework, pas de bundler, pas de build. Le JavaScript du navigateur est en modules ES natifs.
  • Quatre fonctions Vercel dans api/ (plus api/health.js), en JavaScript, qui appellent les règles du domaine de lib/. Elles seules lisent et écrivent la base.
  • Une base Redis Upstash, installée sur le projet Vercel par la Vercel Marketplace : le tirage, les empreintes des mots de passe, les compteurs d'essais.
  • Aucune session : le navigateur ne garde rien entre deux visites (S5). Chaque appel qui donne un tirage ou ouvre la page réservée porte le mot de passe, vérifié à chaque fois.

Les fonctions

Réponses JSON en Cache-Control: no-store. Signature Web de Vercel : export async function POST(request). Les appels POST exigent du JSON (sinon 415) de 2 Ko au plus (sinon 413) ; un participant inconnu donne 400.

AppelCorpsRéponses
POST /api/participant{ participant }200 { hasPassword }
POST /api/choose-password{ participant, password }200 { receiver } · 422 too_short · 409 already_chosen · 429 locked
POST /api/open-gift{ participant, password }200 { receiver } · 401 wrong_password · 429 locked · 409 no_password
POST /api/reserved{ password, action: "list" } ou "erase" avec participant200 { participants: [{ id, name, hasPassword }] } · 400 · 401 · 429 · 503
GET /api/health—200 { ok, store, reservedPage }

Toute autre réponse, une erreur 5xx, un réseau coupé ou aucune réponse en 15 secondes fait afficher « Oups, le site ne répond pas… » sur l'écran en cours.

Choisir son mot de passe (S2, S7)
  1. Moins de 4 caractères, espaces au bout retirés : 422 too_short.
  2. Le tirage est lu ; s'il n'existe pas, il est fait et écrit une seule fois. Avant le mot de passe, pour qu'une coupure ne laisse pas un mot de passe sans paquet.
  3. L'empreinte n'est écrite que si le participant n'en a pas (SET … NX).
  4. S'il en avait déjà une : même mot de passe, le prénom tiré ; autre mot de passe, essai raté compté et 409 already_chosen (l'écran passe à « Redonner ») ; blocage en cours, 429. Un mot de passe n'est jamais remplacé, ni deviné par cet appel.
Redonner son mot de passe (S3)
  1. Pas de mot de passe (effacé entre-temps) : 409 no_password, sans compter d'essai, l'écran passe à « Choisir ». L'effacement retire aussi le blocage.
  2. Participant bloqué : 429 locked, sans vérifier, même le bon.
  3. Essai compté avant la vérification (INCR atomique), puis blocage relu : jamais plus de 5 vérifications, même pour des essais simultanés. Au-delà du cinquième, ou blocage posé entre-temps : 429, sans vérifier. Le cinquième pose le blocage avant sa vérification.
  4. Juste : compteur à zéro (et blocage du cinquième retiré), le prénom tiré.
  5. Faux : au cinquième de suite, compteur à zéro, blocage d'une minute et 429 (c'est lui qui affiche « Beaucoup d'essais ratés… ») ; sinon 401.
La page réservée (S6)

Chaque appel porte le mot de passe d'administration, comparé tel quel à ADMIN_PASSWORD, en temps constant ; même règle des 5 essais, avec l'identifiant admin. Sans ADMIN_PASSWORD, tout appel répond 503 : la page ne s'ouvre jamais sans mot de passe posé. L'effacement supprime l'empreinte, le compteur d'essais et le blocage du participant, et rien d'autre. Jamais de tirage, d'empreinte ni de mot de passe dans la réponse.

Données

Une seule base Redis de production. Valeurs en chaînes, client créé avec automaticDeserialization: false et enableAutoPipelining: false.

Seule la production a une base : secret-santa-kv, reliée au seul environnement Production. Les déploiements de revue n'en ont pas (décision V7).

Le tirage

  • Mélange de Fisher-Yates avec crypto.randomInt, recommencé tant que quelqu'un se tire lui-même : chacun des 1 854 tirages possibles pour sept participants a la même chance, paires réciproques comprises. 2,7 mélanges en moyenne.
  • Lu, et s'il manque, proposé et écrit par SET draw … NX : si deux personnes valident en même temps, Redis n'en garde qu'un, et chacune relit celui-là. Rien ne le supprime ni ne le réécrit.

Les mots de passe

  • Normalisation : espaces au bout retirés, accents retirés (NFD, marques \p{M}), minuscules : « Noël », « noel » et « NOEL » donnent noel.
  • Longueur : au moins 4 caractères, en points de code, sans les espaces au bout, en NFC. Aucune autre règle.
  • Empreinte : scrypt de node:crypto, sel de 16 octets, N = 16384, r = 8, p = 1, 32 octets (74 ms constatés). Vérification par timingSafeEqual. Jamais en clair, jamais dans un journal.

Le stockage

Six opérations, reçues en paramètre par les règles du domaine : get, mget, setIfAbsent, setWithExpiry, incr, del. Le double en mémoire seulement avec SECRET_SANTA_STORE=memory et hors de Vercel ; sinon Redis par Redis.fromEnv(), qui lit KV_REST_API_URL et KV_REST_API_TOKEN (lu dans le code de la version 1.41.0). L'intégration pose, en production seulement, KV_REST_API_URL, KV_REST_API_TOKEN, KV_REST_API_READ_ONLY_TOKEN, KV_URL et REDIS_URL (constaté) ; le site n'utilise que les deux premières. Sans base, comme sur une revue, une erreur, jamais un repli sur la mémoire ; les pages et api/health marchent quand même.

Les écrans

  • Un seul document pour le participant, dont le contenu change à chaque écran, sans entrée d'historique : le retour du navigateur quitte le site au lieu de réafficher un paquet. Une page restaurée depuis le cache du navigateur revient à l'accueil.
  • Rien n'est retenu : ni cookie, ni stockage du navigateur. Le mot de passe tapé et le prénom tiré ne vivent que dans des variables, effacées au retour à l'accueil.
  • La page réservée garde le mot de passe d'administration le temps de la visite ; la recharger le redemande.
  • Le style de la maquette, polices Pixelify Sans et Atkinson Hyperlegible depuis Google Fonts, un seul thème. Ni attribut style ni script en ligne : la politique de sécurité du contenu les refuse.
  • Le compte à rebours prend la date du jour à Paris sur l'horloge de l'appareil.
  • Sur une erreur réseau, une réponse 5xx ou une réponse qui n'arrive pas en 15 secondes, l'écran reste, avec le bandeau et « Réessayer », qui refait le même appel ; ce qui était tapé reste. Un appel dont l'écran a changé depuis ne montre ni sa réponse ni son bandeau.
  • Un seul appel à la fois : tant qu'une réponse est attendue, un nouvel appui sur le bouton d'envoi (et, sur la page réservée, sur « Effacer » ou « Annuler ») ne fait rien. Un double appui ne compte qu'un essai ; pendant le bandeau, le bouton refait l'appel. L'appui sur un prénom de l'accueil, simple lecture, n'est pas gardé.

Hébergement et déploiement

  • Vercel, offre gratuite, projet secret-santa sur le compte yannicktians-projects, relié au repo, une seule adresse. Node.js 26 (engines.node « 26.x »), fonctions en sfo1, la région de la base (région par défaut de l'intégration, non choisie). vercel.json sert public/ sans build, avec cleanUrls pour /reservee.
  • Production : chaque fusion sur main. Variables : celles de l'intégration Upstash, ADMIN_PASSWORD.
  • Revue : chaque branche poussée, sans base ni mot de passe d'administration, derrière l'authentification de Vercel : seules les pages et api/health y marchent. Écrans et fonctions se prouvent par les tests, sur le double en mémoire.
  • Sur la production, les agents ne font que lire sans donnée : GET /, GET /reservee, GET /api/health. Jamais choose-password, open-gift ni reserved : un mot de passe choisi par un agent ferait le vrai tirage.
  • Jeton : la CLI Vercel avec VERCEL_TOKEN, chargé depuis ~/.config/secret-santa/vercel.env, jamais affiché.

Constaté le 22 novembre 2026 : le projet existe, la base est reliée à la seule production avec les variables ci-dessus, et l'offre gratuite d'Upstash n'accepte qu'une base.

Constaté sur le premier déploiement de production, le 22 novembre 2026 : la signature Web des fonctions sans framework, outputDirectory et cleanUrls, la région de la base (détail dans docs/deploiement.md).

Non vérifié : VERCEL_ENV à l'exécution, qu'aucune fonction ne renvoie ; Redis derrière les fonctions, que seule la production montre (lu au constat humain de la tâche 13, écrit au premier mot de passe choisi) ; les quotas, la conservation d'une base gratuite peu utilisée.

Contrôles et tests

  • npm run check : Biome (lint et format), tsc (JavaScript vérifié par JSDoc, strict), node --test.
  • npm run test:e2e : Playwright (Chromium) contre le serveur local sur le double en mémoire, à 360 et 1280 pixels ; avec CAPTURES=1, les captures dans captures/, ignoré par git.
  • Pas de build. Intégration continue GitHub Actions sous Node.js 26 à chaque pull request et poussée sur main : actions épinglées par le SHA de leur commit (actions/checkout v7.0.1, actions/setup-node v7.1.0), npm ci --ignore-scripts (aucune dépendance n'a de script d'installation ; les navigateurs de Playwright viennent de sa commande à part).
  • Node.js 26 pour la CI et Vercel ; le serveur de développement garde Node.js 24, dont d'autres projets dépendent : les contrôles locaux y tournent, npm ci y avertit (EBADENGINE) que engines demande 26, ce qui est attendu. La CI sous Node.js 26 fait foi avant chaque fusion.
  • Dépendances aux versions exactes : @upstash/redis 1.41.0 (seule dépendance du site, plus uncrypto), et pour le développement @biomejs/biome 2.6.8, typescript 7.0.2, @types/node 26.6.6, @playwright/test 1.65.1, installées et essayées le 22 novembre 2026.

Règles pour les tâches

  • Taille : 400 lignes modifiées au plus, hors tests, package-lock.json et captures.
  • Chemins sensibles : api/**, lib/**, scripts/dev-server.js, tests/securite/**, vercel.json, package.json, package-lock.json, .gitignore, .github/**, docs/architecture.md, docs/specs/**, AGENTS.md, CLAUDE.md. Fusionnés après relecture sans validation humaine (restrictions du projet), avec une relecture de sécurité en plus. public/** n'est pas sensible : le test de fuite garde ce que les pages reçoivent.
  • Données : rien de réel nulle part ; ni .env, ni base de production, ni ADMIN_PASSWORD pour les agents.
  • Captures : à 360 et 1280 pixels, dans les états de la spec, par les tests de la tâche, comparées à la maquette.
  • Fichiers partagés : l'architecture ne change que pour corriger un écart ; pas d'entrée de CHANGELOG dans une tâche.

Hypothèses et ce qui n'est pas conçu

  • L'horloge de l'appareil donne le jour du compte à rebours.
  • Une seule base, sans sauvegarde : perdue, le tirage le serait aussi. Ce qu'Upstash fait d'une base gratuite peu utilisée n'est pas vérifié.
  • Pas de journal des actions ; les journaux de Vercel ne reçoivent ni mot de passe, ni empreinte, ni tirage.
  • Pas de domaine propre : l'adresse que Vercel donne.
  • Non conçu, hors périmètre : ajout ou retrait d'un participant, second tirage, autre année.
